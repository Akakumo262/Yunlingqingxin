## 总目标

把当前“接口契约 + mock/内存参考实现 + 局部 PostgreSQL/RLS 基础 + 三端页面”提升为可持续开发、可联调、可安全验收的真实产品：

- 学生端、家长端、教师端、管理端使用同一个真实后端和同一套数据边界。
- 学生端“发现”能从允许访问的权威来源获取真实内容，并保留原文链接。
- 后端数据落 PostgreSQL 16，所有租户和角色权限可验证。
- 关键流程能端到端跑通，失败可定位，测试可重复执行。

## 必须保持的兼容性

- 保留现有 `contracts` 的 59 个接口、字段、角色和错误码语义。
- 不随意删除或重命名现有字段；新增字段优先设为可选，并同步 mock、前端类型、构建和验收脚本。
- 保留学生/家长的隐私边界：学生端和家长端不显示内部风险等级或处置标签；家长只看允许展示的摘要；小样本聚合结果要抑制；学生个案数据不能被越权访问。
- 现有 `frontend/miniapp` 是学生端 + 家长端，`frontend/web` 是教师/管理端；不要把各端重新拆成互不兼容的系统。

## 实施顺序

### 阶段一：基线与真实后端

- 把 `backend` 从 `createMock()`、内存状态和临时适配迁移到 PostgreSQL 16 + Kysely。
- 完成可重复的 `migrate`、`seed`、`reset`、启动和 Windows 文档。
- 让 59 个接口都具有真实的读写路径，不留下假成功、隐式内存状态、未处理的 501/TODO。
- 事务、幂等、并发更新、分页、排序和错误响应要明确。
- 保留 fixture/mock provider 作为离线测试入口，但生产路径必须能切换到真实数据库。

### 阶段二：安全与隐私

- PostgreSQL 多租户强制 RLS；应用连接使用非属主账号；每个事务显式设置租户上下文。
- JWT 短时效、刷新轮换与撤销；密码使用 Argon2id 或 bcrypt；所有输入使用 zod 或等效 schema 校验。
- 参数化 SQL、统一 RFC 9457 错误响应、角色/目的码/数据域校验、字段脱敏。
- 敏感字段使用 AES-256-GCM 或等效方式加密；审计日志追加写入并带哈希链，不能泄露原文隐私。
- 补齐跨租户读取/写入、越权、注入、重放、限流、审计完整性和敏感字段检查。

### 阶段三：真实“发现”内容管道

- 增加来源、内容、抓取运行记录、审核记录、去重指纹等持久化结构。
- 设计 provider 适配器，优先接入公开且允许访问的权威来源，例如教育部、团中央、中国青年志愿者、全国大学生创业服务网等；来源需可配置，不要硬编码成不可替换的爬虫。
- 实现定时抓取、超时、重试、退避、去重、清洗、发布时间/截止时间/地区/适龄阶段解析、原文 `external_url` 保留。
- 遵守 robots、网站条款和访问频率；不绕过登录、验证码、封禁或技术限制。
- 内容必须经过来源白名单和人工/规则审核后再进入学生和家长可见流。抓取失败时记录状态并支持人工补录，不得伪造“已核验”。
- 默认使用 fixture provider；只有明确配置开关后才访问外网，便于本地开发和测试。

### 阶段四：学生端发现和家长端

- 学生“发现”支持 AI 资讯、竞赛、志愿、职业等频道和筛选。
- 根据学生阶段、地区、兴趣做可解释的个性化排序；显示来源核验状态、发布时间、截止时间和适用范围。
- 支持内容详情、原文跳转、复制链接兜底、收藏、已读、反馈和失效链接提示；新增接口时保持旧接口兼容。
- 家长端只展示适合家长的摘要、支持建议、课程和经审核的资源，不泄露孩子的原始量表、逐日记录、咨询内容或内部标签。

### 阶段五：三端联动

至少跑通并提供测试数据和 E2E 脚本：

1. 学生求助 → 教师收到预警 → 教师确认/升级 → 家长获得合规摘要。
2. 学生激活 → 家长绑定 → 同意/撤回 → 权限立即生效。
3. 内容发布/审核 → 学生和家长按受众看到正确内容 → 原文跳转可用。
4. 教师个案/转介 → 协作机构处理 → 回执回到学校 → 审计可追溯。

前端统一调用真实 `Routes`/API，不要让各端各自维护一份互不相通的 mock 状态。

### 阶段六：AI 与工程质量

- AI 使用“护栏 → 检索 → 生成 → 输出后检查”链路；只检索已发布内容、生涯卡和政策。
- 危机命中时不调用模型，给出人工帮助路径和 12355 等配置化资源；无模型密钥时提供本地检索式降级。
- 做好脱敏、不训练、保留期限、来源追溯和提示词注入防护。
- 补健康检查、OpenAPI、结构化日志、指标、错误追踪和运行状态页。
- 补单测、集成测试、RLS/安全测试、最小 E2E/联调脚本；构建 `contracts`、`backend`、`frontend/web`、`frontend/miniapp`。
- 让 `npm run accept` 面向真实后端通过；发现失败时给出最小复现步骤和修复说明。

## 工作方式和交付要求

- 每个阶段先运行现有测试，再修改，再运行相关测试；不要用删测试或降低断言来“通过”。

- 最终输出必须区分：已完成、仍未完成、外部阻塞、下一步命令，以及真实验收证据。
